# 活动缓存与网关限流实测

## 结果

缓存与限流专项通过 89 项检查；原有活动管理、真实库存准备与购买回归通过 104 项检查。构建 Event、Gateway 及依赖成功。

同一热点活动的 64 次冷缓存请求，在两个 Event 进程间共同重建，MySQL 记录 1 次业务 SELECT。预热后的 2,000 次查询全部成功，业务 SELECT 为 0。两个网关共享调用方额度，低额度压测中 2,000 次请求放行 5 次、拒绝 1,995 次。

## 测试条件

- 本机 Windows、Java 17.0.20，MySQL 和 Redis 运行于同一台机器；具体机器沿用此前本机性能基线。
- 32 个客户端工作线程，有限请求、无客户端自动重试。每阶段查询同一个已发布活动详情。
- 两个独立 Event JVM、两个独立 Gateway JVM；Auth 与驱动在同一个 JVM。随机端口、测试库及 Redis 前缀隔离。
- 本轮关闭 Nacos 注册，使用测试进程的固定 HTTP 地址；用于验证跨进程共享 Redis，不测服务发现或多机网络容量。
- Event 回源并发额度在本次对照中覆盖为 64，避免把冷启动时默认 16 额度的拒绝混入查询吞吐对照；正式默认值仍为 16，回源拒绝单独验证。数据库连接池保持默认配置。
- 网关稳定缓存阶段关闭限流；限流阶段覆盖活动全局额度为 10000/秒、桶容量 10000，调用方额度为 1/秒、桶容量 4，便于明确核对共享额度。订单额度另设全局 1/秒、容量 3，用户 1/秒、容量 2，用于核对双桶。
- 网关启动和边界验证可能超过正常缓存 TTL，因此网关稳定缓存阶段单独预热 100 次。预热、重启及边界检查不计入下表。

## 专项检查

- 活动详情、分页、场次 VO 在不同进程之间正确反序列化，每个响应重新生成 traceId。
- 内部购票规则在展示缓存存在时仍读取数据库中的新价格。
- 同一个不存在的活动被查询 12 次只回源 1 次；成功发布后其他实例的空结果和列表缓存失效。
- 发布失败和事务回滚保持缓存版本，事务提交后切换版本。
- 租约过期后新请求可重建，旧请求不能覆盖新缓存，也不能释放其他持有者的锁。
- 重建等待有期限；回源额度用尽时拒绝额外工作并正确归还额度。
- 损坏的 JSON 可重新加载，丢失版本键不会重新命中旧版本缓存。
- Event Redis 不可访问时受控查库；限流 Redis 不可访问时网关返回 503。
- 两个网关共享匿名 IP 桶，伪造 `X-Forwarded-For`、`X-User-Id` 不能获得新额度。
- 不同真实登录用户有独立调用方桶，但仍共享全局桶；被限流请求未转发到订单探针，匿名订单请求仍返回 401。
- 原有活动管理回归保留真实库存初始化、异常恢复、内部服务凭证和购买流程校验。

专项中的库存准备使用隔离数据库夹具，订单限流使用 HTTP 探针，不能替代真实交易验收。原有回归关闭缓存和限流，用于单独核对业务行为；专项负责新功能及故障边界。

## 复现与限制

启动 MySQL、Redis，打包相关服务后运行：

```powershell
& deploy/verify/verify_event_cache_load.ps1
& deploy/verify/verify_event_administration.ps1
```

驱动读取已有数据库和 Redis 环境变量，自动清理自己创建的进程、随机库和命名空间。专项原始日志和汇总保存在忽略目录 `.local/event-cache-verification/<运行ID>/`。

这是短时间、单热点、本机两实例的功能压力对照。未验证固定到达率、长期运行、多机容量、Redis主从切换或集群故障；不能据此承诺生产 QPS。活动查询优化没有改变库存热点行竞争、下单写库或支付出票吞吐。
