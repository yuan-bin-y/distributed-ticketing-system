# 票务平台设计草案（第一版）

本文件先固定学习项目的业务范围与关键规则。实现过程中如需改变服务边界或交易语义，先更新本文件，再修改代码。

当前下单阶段已接入订单数据库、购买幂等、活动规则校验、库存预留、持久化恢复和未支付到期释放，具体实现约定见 [订单创建与恢复](order-workflow.md)。认证、用户累计限购、支付、Outbox/MQ 仍未实现；下文保留各历史阶段的验证记录。

## 1. 目标与范围

面向演唱会、体育赛事等活动，实现按**场次 + 票档**购买的最小交易闭环：

1. 用户注册、登录，浏览活动、场次、票档与可售状态。
2. 管理员创建、上架活动，设置场次、票档、开售时间、库存与每人限购量。
3. 开售后提交抢票请求；系统校验身份、时间、限购规则并预留库存。
4. 创建待支付订单；模拟支付成功后确认订单并生成电子票。
5. 订单超时或创建失败时释放预留；用户可查看订单和电子票。

第一版不做座位图、指定座位、真实第三方支付、主动退款、通知服务和分库分表。模拟支付仍需处理重复回调、超时后成功回调等异常，并记录模拟退款/冲正结果。后续版本再扩展这些能力。

## 2. 服务与数据边界

| 组件 | 拥有的能力与数据 | 对外协作 |
| --- | --- | --- |
| `ticket-gateway` | 入口路由、身份校验、基础限流；无业务表 | 将请求路由到业务服务 |
| `ticket-auth-service` | 用户、凭证、登录状态 | 提供身份信息；其他服务不读其数据库 |
| `ticket-event-service` | 活动、场次、票档、开售规则 | 提供活动查询与规则快照 |
| `ticket-inventory-service` | 票档库存、预留记录、售出记录 | 提供预留/确认/释放命令 |
| `ticket-order-service` | 订单、订单项、状态和购买幂等键 | 协调下单，处理支付结果与超时 |
| `ticket-payment-service` | 模拟支付单、支付结果、模拟冲正记录 | 产生支付结果事件，处理迟到成功 |
| `ticket-common` | 极少量通用异常、响应等基础代码 | 不放业务实体和数据库访问代码 |

服务分别持有自己的数据库或独立 schema；**只允许服务修改自己拥有的数据**。同步调用用于下单所需的即时校验和预留，消息用于支付结果等跨服务状态传播。跨服务共享的请求/响应契约可放在独立 API 模块，但不能把所有服务的实体、Mapper 和业务逻辑集中进去。

第一版服务较多，按阶段启动：先 Gateway、Nacos、Event；再 Inventory、Order；最后 Auth、Payment。开发早期可用固定测试用户贯通订单链路，再接真实认证。

## 3. 核心数据与状态

库存按 `session_id + ticket_tier_id` 维护：总量、已预留量、已售量。始终满足 `已预留量 + 已售量 <= 总量`。库存服务以数据库条件更新/事务作为最终裁决；Redis 可做热点读缓存、入口预筛和限流，不能作为唯一库存事实来源。

每次预留有独立 `reservation_id`、订单关联、到期时间和状态：`RESERVED -> SOLD` 或 `RESERVED -> RELEASED`。这两个终态不可互相转换；确认和释放都须幂等。

订单状态：`PENDING_PAYMENT -> PAID -> COMPLETED`；未支付到期走 `PENDING_PAYMENT -> CANCELLED`。状态变更使用带前置状态的条件更新，防止支付成功和超时取消同时生效。支付单单独记录支付及模拟冲正状态。电子票以订单项为唯一来源，重复支付消息不可重复出票。

## 4. 交易流程与异常

### 下单

1. Gateway 完成入口校验和限流；订单服务校验用户、开售时间和限购规则。
2. 客户端提供请求幂等键；订单服务用唯一约束阻止重试产生第二笔订单。
3. 库存服务在本地事务中条件预留库存，返回 `reservation_id` 和到期时间。
4. 订单服务落库待支付订单；若失败则发起幂等释放。若此时进程崩溃，库存服务扫描过期预留并向订单服务核对：订单已支付则确认售出，已取消或不存在才释放；状态暂时无法确认则重试，不能仅凭预留到期时间释放。

### 支付与出票

1. 模拟支付服务记录支付结果，并通过 Outbox 发布支付成功事件。
2. 订单服务按支付单 ID 幂等消费，只能将 `PENDING_PAYMENT` 条件更新为 `PAID`。
3. 库存服务幂等地将对应预留确认为售出；订单服务最终生成唯一电子票并置为 `COMPLETED`。
4. 消息可重复、可延迟；消费者需要去重、重试、死信处理及人工可查的补偿记录。

### 超时与迟到支付

订单到期任务只能将 `PENDING_PAYMENT` 改为 `CANCELLED`，然后通知库存服务释放预留。释放失败持续重试，库存预留过期扫描按订单最终状态核对兜底。若支付成功事件到达时订单已经取消，不得重新售票；支付服务记录并执行模拟冲正。支付和取消的竞争结果由订单状态条件更新决定。

跨服务流程不依赖一个覆盖所有数据库的 `@Transactional`。第一版使用本地事务、Outbox、幂等消费、重试及补偿实现最终一致性，并提供可核对的订单、预留、支付和票据记录。

## 5. 学习技术与引入顺序

| 阶段 | 技术 | 要解决的问题 |
| --- | --- | --- |
| 基础链路 | Spring Cloud Gateway、Nacos、Spring Cloud LoadBalancer、服务间 HTTP 调用 | 路由、发现、配置与服务调用 |
| 交易核心 | MySQL 条件更新与唯一约束、Redis、RabbitMQ、Outbox | 不超卖、幂等、跨服务最终一致 |
| 稳定性 | 网关限流、超时、熔断/降级、重试边界 | 洪峰与故障隔离 |
| 可观测性 | Micrometer/OpenTelemetry、Prometheus/Grafana、链路追踪 | 定位慢请求和失败链路 |
| 验证 | 集成测试、并发压测、故障注入 | 用数据证明正确性与吞吐量 |

服务间 HTTP 客户端可先选一种实现并理解超时、重试和负载均衡；OpenFeign 可用于学习，Spring 官方也建议新项目考虑 HTTP Service Clients。Sentinel、Seata、ShardingSphere 留作专题学习，只有出现明确需求时再加入。具体依赖版本应在搭工程时根据 Spring Boot、Spring Cloud 和 Spring Cloud Alibaba 的官方兼容表确定，不凭已有项目版本拼接。

## 6. 第一版验收标准

- 活动查询、下单、模拟支付、出票、超时取消可从 Gateway 端到端跑通。
- 并发请求数超过库存时，成功售出的数量不超过库存；测试结束后预留、售出、可售数量可核对。
- 同一用户同一场次超出限购量会被拒绝；同一幂等键重复提交只产生一笔订单。
- 重复支付回调、重复消息、重复取消任务不会重复扣减、释放或出票。
- 人为让订单服务在预留后失败、让消息消费暂时失败，系统最终恢复，或留下可定位并可重试的补偿记录。
- 压测报告记录环境、库存、并发量、成功/失败数、吞吐量、延迟分位数和数据库核对结果；不把设想的“5 万人抢票”写成实测能力。

## 7. 实施里程碑

1. **基础链路**：父 POM/BOM、Nacos、Gateway、Event 服务；通过网关查询数据库中的活动与场次。
2. **抢票链路**：Inventory 与 Order 服务；完成预留、订单创建、限购、幂等和到期释放。
3. **支付闭环**：Auth、模拟 Payment、Outbox/MQ、出票及迟到支付补偿。
4. **治理与证明**：限流、故障隔离、监控追踪、并发与故障测试，形成可复现的结果报告。

### 当前 Order → Inventory 接入步骤

订单服务新增 `InventoryClient`，通过 RestClient、Nacos 和 LoadBalancer 按服务名调用库存服务的预留、确认、释放和预留查询接口。订单服务定义自己的请求/响应契约，不依赖库存模块和数据库。Event、Inventory 使用各自有明确名称的 HTTP Builder，独立配置连接/读取超时，均不自动重试。

新增 `POST /internal/orders/stock-reservations` → `OrderService.reserveStock` → `InventoryClient.reserve`，让库存调用真实经过订单业务层。该接口是服务内部库存协作入口，接收稳定的 `orderId`、`sessionId`、`ticketTierId`、`quantity`、`expiresAt`，返回预留结果；此内部演示接口不创建订单、不检查活动规则或用户身份。正式下单已在后续阶段使用独立的 `POST /api/orders`，累计限购仍待实现，已有 `/api/orders/preview` 继续只做预览。网关不新增内部路由。

客户端校验成功响应的预留 ID、订单编号、场次、票档、数量、到期时间和状态。预留重试允许返回原记录的 RESERVED、SOLD 或 RELEASED；确认只接受 SOLD，释放只接受 RELEASED。库存符合契约的 400/404/409 作为参数、资源及业务冲突处理；不可用、超时、错误契约分别返回 503/504/502。重定向不作为成功。超时或连接失败可能发生在库存提交之后，不自动释放，也不把调用失败当作库存未变更；调用方需沿用同一编号及全部参数重试，或通过已知预留 ID 核对状态。

### 当前库存步骤的接口与事务约定

新增独立的 `ticket-inventory-service`（8063），使用 `ticket_inventory` 库。仍沿用 Controller → Service → Impl → MyBatis-Plus Mapper、DTO/VO、Result 和 Flyway。

- `t_ticket_stock`：票档 ID 为主键，保存所属场次、总量、可用量、预留量、售出量。数据库检查各数量非负且 `总量 = 可用量 + 预留量 + 售出量`。场次与票档 ID 只是活动服务的标识，不建立跨库外键；票档 ID 全局唯一，因此也能唯一确定场次下的库存。
- `t_stock_reservation`：独立的 32 位 UUID 预留 ID，唯一的订单关联编号 `order_id`，以及场次、票档、数量、到期时间、状态。第一版每个订单只买一个票档，订单服务应在预留前生成稳定的订单编号，后续重试沿用同一编号和参数。
- 预留请求参数为 `orderId`、`sessionId`、`ticketTierId`、`quantity`、`expiresAt`；时间为东八区本地时间，精度最多毫秒。首次预留到期时间必须晚于当前时间。同一编号必须携带相同参数，重复请求返回已有记录的当前状态；已经释放的编号不会再次扣库存。
- 内部接口为 `POST /internal/stock-reservations`、`POST /internal/stock-reservations/{reservationId}/confirm`、`POST /internal/stock-reservations/{reservationId}/release`，另提供预留和库存的内部查询。网关不添加库存内部路由，服务身份认证按后续认证阶段实现。
- 预留先通过唯一键插入或锁定预留记录，再用 `available_quantity >= quantity` 的条件更新扣可用量、加预留量；库存不存在、场次不匹配或不足时整笔事务回滚。重复键不会覆盖原请求参数。
- 确认和释放先锁定同一预留记录，再按 `RESERVED` 前置状态修改记录和库存；同方向重复操作直接返回结果，互相冲突的终态操作返回 409。各命令采用本地事务，所有路径遵守先预留记录、后库存记录的锁顺序。锁竞争失败返回可重试的 503，不能当作成功。
- 当前仅实现数据库库存命令。库存由本地演示 SQL 手动初始化；不自动读取活动库，不接 Redis/MQ，不创建订单。到期时间用于后续核对任务，本阶段不会仅凭到期时间自动释放库存。

重复请求串行化使用 MySQL `INSERT ... ON DUPLICATE KEY UPDATE` 配合锁定读取，见 [MySQL 8.0 锁说明](https://dev.mysql.com/doc/refman/8.0/en/innodb-locks-set.html)。预留表不对库存建立外键，避免插入预留时的父记录共享锁与库存更新产生锁升级竞争；关联存在性由同一事务的库存更新验证。
