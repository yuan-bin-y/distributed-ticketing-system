# 第一版技术栈与简历描述

本项目为独立学习项目，围绕票务交易演练服务协作、库存并发与故障恢复。简历应结合自己能够解释的实现和真实测试结果使用以下内容。

## 当前技术栈

| 技术 | 项目中的用途 |
| --- | --- |
| Java 17、Maven 多模块 | 聚合构建、依赖版本管理与公共代码复用 |
| Spring Boot 4.0.8、Spring Cloud 2025.1.3、Alibaba 2025.1.0.0 | 微服务基础依赖；版本来自当前父 POM |
| Spring Cloud Gateway、WebFlux | 统一路由、响应式 JWT/Redis 会话准入 |
| Nacos 3.1.2、Spring Cloud LoadBalancer、RestClient | 注册发现、实例选择与服务间 HTTP |
| Spring Security、RSA JWT、BCrypt、Redis | 用户登录、会话刷新和退出、业务归属检查 |
| MySQL、MyBatis-Plus 3.5.17、Flyway | 数据访问、条件更新、唯一约束、本地事务与版本迁移 |
| 持久化状态、领取租约、幂等、补偿 | 不确定网络结果、多实例竞争与宕机恢复 |
| Java 验证程序、PowerShell、可选耗时日志 | 并发与故障注入、可复现验收、连接池和数据库等待观测 |

## 相比已有单体项目重点学习的内容

常规 Controller → Service → Mapper、登录、基础 Redis 和 CRUD 可复用已有经验。本项目新增重点是：服务进程及数据所有权、Nacos 实例发现、HTTP 契约与失败分类、网关响应式过滤、用户身份与服务身份分离，以及跨服务流程在超时和宕机后如何继续。

数据库本地事务只能回滚自己的数据。如何辨认“对方未执行”与“对方执行了但响应丢失”，如何用原请求幂等核对、恢复订单进度和迟到付款冲正，是项目需要讲清楚的核心。

## 简历可用描述

**分布式票务交易平台｜个人学习项目**

技术栈：Spring Boot、Spring Cloud Gateway、Nacos、LoadBalancer、RestClient、Spring Security、JWT、Redis、MySQL、MyBatis-Plus、Flyway。

- 按认证、活动、订单、库存、支付划分服务及独立数据库，通过 Gateway 和 Nacos 完成统一入口、注册发现与 HTTP 协作，实现活动发布、下单、模拟支付和电子票闭环。
- 使用 MySQL 条件更新及本地事务控制库存预留、确认和释放，结合购买幂等键、预留唯一约束与累计限购，验证并发竞争及重复请求下的数据正确性。
- 基于订单持久化状态、任务租约、幂等核对和重试补偿处理响应丢失、服务重启、到期关闭及迟到付款；支付通知后回查付款事实，无法履约时进行全额模拟冲正。
- 完成真实 Nacos/Gateway 验收与限购、支付恢复共 312 项检查；建立单机并发测试及连接池/SQL 耗时观测，定位热点库存行竞争。

如需加入性能数据，可追加：“在单机、256 工作线程、每组 1,000 次下单对照中，单热点约 65 请求/秒；同场次十票档分散请求约 152 请求/秒，库存与订单核对通过。”引用 [对照报告](performance/comparison-2026-10-06.md)中的环境和边界，不能写成生产容量或支付出票吞吐。

## 面试介绍顺序

1. 业务目标：按票档购票，模拟支付，生成电子票；没有指定座位与真实资金。
2. 服务拆分依据：谁拥有数据、哪些变更需要本地原子性、服务向外提供哪些契约。
3. 一条完整调用链：Gateway → Order → Event 查询规则 → Order 保存订单 → Inventory 预留。
4. 最难的失败场景：库存已扣但响应丢失，保持原编号核对；库存已释放后付款，走模拟冲正。
5. 如何证明正确：隔离库、并发、响应丢失、宕机重启、重复操作与订单/库存/票券核对。
6. 性能发现与下一步：扩连接不一定增加吞吐；热点行需要结合观测优化，第二版再加入 MQ/Outbox 等能力。

## 描述边界

未实现的 RabbitMQ、Outbox、Seata、Sentinel、限流、熔断、分库分表及完整可观测平台列为后续计划。该项目是学习与本机验证成果，不能描述为生产运营、多机压测、真实支付经验或已支持万人抢票。
